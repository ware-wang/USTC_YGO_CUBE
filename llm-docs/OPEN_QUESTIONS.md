# Open Questions

这些问题目前还没有彻底回答，后续模型接手时可以优先留意。

## 1. 浏览器端到端链路是否已经完全跑通？

目前已完成：

- 服务启动验证
- REST 验证
- duel 协议脚本验证
- `/neos/duelroom -> /neos/duel` 真实浏览器入局验证
- 黑森林的魔女送墓检索后的连锁结束 / 自由时点回归验证

但还缺一轮完整业务流的浏览器回归：

- 建房
- 双人入房
- 开始轮抽
- 完成选牌
- 组卡提交
- 打开 neos 对战
- 打完至少一个基础操作回合

## 2. 缺 Lua 脚本的卡在真实对局里会造成什么级别的问题？

目前知道：

- `DuelSession` 会跳过缺脚本卡并打日志

还不知道：

- 是否只是少数测试卡
- 是否会让双方牌组失衡
- 是否会在某些局面下直接无法继续

## 3. `duel_start` / `duel_respond` 等老消息是否还有前端在使用？

当前已做保护，但还不确定：

- 是否有旧页面、旧脚本、旧外部调用仍依赖它们

## 4. `battle_tables_created` / `battle_tables_ready` 的兼容是否还需要长期保留？

现在为了保险，两边都兼容了。

后续可以考虑：

- 统一到一个消息名
- 清掉兼容分支

前提是确认没有旧前端再依赖旧名字。

## 5. README 中是否还存在别的“历史描述残留”？

这轮已经修了 duel 入口相关部分，但整个 README 仍可能有别的旧描述未被发现。
